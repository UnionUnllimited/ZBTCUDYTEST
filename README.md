# Titan Router Firmware

OpenWrt-прошивка с PassWall для обхода блокировок.

## Устройства

| Устройство | Profile | WAN | LAN |
|---|---|---|---|
| ZBT Z8103AX-C | `zbtlink_zbt-z8103ax-c` | eth1 | lan1–lan3 |
| Cudy TR3000 v1 | `cudy_tr3000-v1` | eth0 (2.5G) | eth1 |
| Cudy WR3000S v1 | `cudy_wr3000s-v1` | wan | lan1–lan4 |
| Cudy WR3000E v1 | `cudy_wr3000e-v1` | wan | lan1–lan4 |

## Структура

```
files-common/   общее: passwall, frpc, панель, скрипты, watchdog
files-zbt/      ZBT Z8103AX-C
files-cudy/     Cudy TR3000 v1
files-wr3000s/  Cudy WR3000S v1
files-wr3000e/  Cudy WR3000E v1
```

Сборка склеивает `files-common` с профилем устройства и собирает образ
через OpenWrt Image Builder. Запускается пушем в `main`.

## После прошивки

- Панель: `http://192.168.14.1/` — логин `admin`, пароль `admin`
- LuCI: `http://192.168.14.1/cgi-bin/luci` — логин `root`
- Wi-Fi: `Titan-2.4` и `Titan-5`, **открытые, без пароля** — клиент
  задаёт пароль в мастере настройки при первом входе в панель
- Пароль root вычисляется из MAC адреса br-lan, см. `etc/rc.local`
- IPv6 отключён полностью

Первую прошивку со стока ставить только **без сохранения настроек**: с
сохранением остаётся старый `/etc/config`, и профиль устройства не
применяется. Дальнейшие обновления идут с сохранением — установщик
отличает их по маркеру `/etc/titan_installed` и не трогает Wi-Fi, пароль
панели и LAN.

## Обновления

Обновление прошивки одно — `usr/bin/titan_ota.sh`, ночью по cron. Он
берёт манифест по адресу из `atl_panel.main.ota_url`, сверяет `version` с
`/etc/titan_version`, проверяет свою волну по хешу MAC, качает образ,
сверяет sha256, прогоняет `sysupgrade -T` и прошивает с сохранением
настроек. Пока `ota_url` пуст, скрипт молча выходит.

```
uci set atl_panel.main.ota_url='https://…/manifest.json'
uci commit atl_panel
titan_ota.sh check   посмотреть, что доступно, без установки
titan_ota.sh now     обновить немедленно, минуя волну и задержку
```

Зеркал может быть несколько — `add_list`, перебираются по порядку.
Формат манифеста и порядок раскатки описаны в `TITAN_OTA_SERVER_SPEC.md`.

Тот же скрипт запускается из панели: меню → «Обновить роутер», карточка
«Обновление прошивки». Кнопка «Проверить» вызывает `titan_ota.sh check`,
«Обновить сейчас» — `titan_ota.sh now`, то есть ставит версию сразу, не
дожидаясь своей волны раскатки и ночного часа. Ход дела панель забирает
опросом `?action=api_ota` и показывает выводом скрипта; когда начинается
`sysupgrade`, она сама ждёт роутер и перезагружает страницу.

Старое ручное обновление через `routeratl/update.sh` убрано: параллельный
механизм с собственными адресами тянул старые параметры. Опции
`upd_script_url` и `upd_version_url` вычищаются из конфигов уже прошитых
роутеров в `uci-defaults/60_atlanta_panel`.

## Переименованные опции PassWall

26.8.26 переименовал часть опций в `@global[0]`, а старые удаляет своей же
миграцией (`migrate_option` в `etc/uci-defaults/luci-app-passwall` внутри
пакета) на первой загрузке после прошивки:

| было | стало |
|---|---|
| `tcp_node` | `node` |
| `udp_node` | удалён, узел теперь один |
| `tcp_node_socks_port` | `node_socks_port` |
| `log_tcp` | `log_node` |
| `log_udp` | удалён |

Ошибка тихая и неприятная: конфиг остаётся валидным, PassWall работает, а
всё, что читало старое имя, видит пустоту. Панель из-за этого не
подсвечивала активный сервер (показывала первый по списку вместо
балансировщика), а кнопка «Применить» писала в опцию, которую PassWall
больше не читает, — смена сервера молча откатывалась на следующей загрузке.

Панель и `stats` теперь читают `node` с откатом на `tcp_node`, пишут в оба.
`uci-defaults` дополнительно проверяет, что узел вообще существует, и
подставляет балансировщик, если он пуст или указывает на исчезнувшую
секцию (так бывает после обновления подписки). Балансировщик ищется по
`protocol='_balancing'`, а не по имени: имя приходит из подписки.

## URL Test в панели

Проверка меряет время TCP-хендшейка и судит **только по нему**. По коду
возврата curl судить нельзя: на портах узлов живёт VLESS или Reality, и
обычный HTTP-запрос там отвечать не обязан — сервер соединение примет и
молча закроет, curl отдаст 52 или 56. Пока проверка требовала нулевого
кода, все рабочие узлы поголовно показывались как «✗».

Подписи в списке серверов строятся от чистого имени, запомненного в
`data-base`, а не срезанием метки регуляркой с хвоста. Прежний способ
не работал дважды: `option.text` по спецификации возвращает текст со
схлопнутыми пробелами, а метка дописывалась через два — регулярка искала
два пробела, находила один и добавляла ещё одну метку поверх старой
(«Германия ✗ ✗»). А класс `[🟢🟡🔴]` без флага `u` разбирается как
половинки суррогатных пар, так что цветные метки не срезались вообще.

## Перезапуск PassWall и лавина

Все перезапуски идут через `usr/bin/titan_pw_restart.sh` — лок на время
работы плюс пауза 5 минут после. Причина: во время перезапуска xray и
chinadns-ng отсутствуют, то есть перезапуск создаёт ровно то условие, по
которому watchdog требует следующий. 29.08.2026 это сложилось вживую —
`vpn_watchdog` и `dns_watchdog` в одну секунду запустили по рестарту,
нагрузка росла три окна подряд (load 4.5 → 10.6 → 18.0), роутер перестал
отвечать.

Оттуда же три сопутствующие правки:

- watchdog'и не работают первые 300 секунд аптайма — PassWall стартует с
  задержкой `global_delay.start_delay`, и проверка внутри этого окна
  требует перезапуска ровно тогда, когда сервис ещё только поднимается;
- минуты в кроне разведены и нигде не совпадают: vpn `:05 :15 …`,
  dns `:01 :06 …`, frp `:03 :08 …`;
- `titan_pw_restart.sh` перед перезапуском сносит недостроенную таблицу
  `inet passwall` (меньше пяти цепочек). Если `app.sh` упал на полпути,
  дальше каждый рестарт сыплет «Could not process rule: No such file or
  directory», и вручную это лечится только сносом таблицы.

Смена сервера из панели идёт мимо этой обёртки намеренно: осознанное
действие клиента не должно проглатываться паузой. Отметку она при этом
ставит ту же, чтобы watchdog'и не набросились сверху.

## Ловушка всплесков нагрузки

`usr/bin/titan_loadwatch.sh`, раз в минуту по крону. Пока `loadavg` ниже
порога — не пишет ничего и флеш не трогает. Выше — дописывает срез
(`top`, `free`, `ps`) в `/etc/titan_load.log`, не чаще раза в 5 минут,
с обрезкой до 400 строк.

Файл в `/etc` и в `sysupgrade.conf` не случайно: из полки роутер выходит
перезагрузкой, а она уносит и syslog (он живёт только в RAM), и весь
`/tmp`. Симптом уносил улики — смотреть было нечего.

## Списки маршрутизации

Три списка, все с `vbotrouters.titanvps.click`:

| Список PassWall | Файл | Что делает |
|---|---|---|
| `chnlist` | `direct-domains.lst` | российские домены мимо туннеля |
| `chnroute` | `direct-ip.lst` | российские подсети мимо туннеля |
| `gfwlist` | `proxy-domains.lst` | наше, чему туннель нужен вопреки |

`chn_list=direct` — то есть содержимое chnlist и chnroute идёт напрямую,
всё остальное падает в `tcp_proxy_mode`/`udp_proxy_mode`, а там `proxy`.

`gfwlist` переиспользован не по названию. Это единственный список PassWall,
который тянется по URL и **всегда** уходит в туннель: переключателя
direct/proxy у него нет, только флаг `use_gfw_list`. Правила применяются
раньше chnlist, поэтому домен на `.ru` из этого файла перебивает общий
direct — так в туннель попадают `nezha.mgsm163.ru` и прочая своя
инфраструктура. Работает на обе стороны: nftables уводит трафик, а
chinadns-ng получает `gfwlist-file` и резолвит эти домены доверенным DNS.

Две ловушки gfwlist, если будете его пополнять. Первая: `rule_update.lua`
сначала прогоняет файл через base64-декодер и берёт как есть только когда
декодирование провалилось — спасает точка в домене, она не входит в алфавит
base64. Голые слова без точки класть туда нельзя. Вторая: список качается с
`exclude_domain=true`, и 17 доменов молча выкидываются — `apple.com`,
`baidu.com`, `qq.com`, `bing.com` и подобные, перечислены в `rule_update.lua`.

Адреса на `raw.githubusercontent.com` убраны: GitHub замедлен, и когда он
отвечает по минуте, обновление уходит в таймаут целиком.

Расписание — штатное, PassWall умеет его сам: Loop Mode раз в 12 часов,
`global_rules.update_week_mode='8'` и `update_interval_mode='12'`. Раньше
в конфиге лежали `auto_update`, `week_update` и `interval_update` — имена
из старых версий, эта их не читает, поэтому на вкладке Rule status режим
показывался как Disable и расписание не работало вообще.

Сверху — `usr/bin/titan_lists_update.sh` из `hotplug.d/iface/20_titan_lists`,
на подъём WAN. Он нужен потому, что Loop Mode устроен так: `tasks.sh`
начинает отсчёт с нуля и первый заход делает только через полный интервал,
а `hotplug.d/iface/98-passwall` перезапускает passwall на каждом ifup —
вместе с ним заново стартует и `tasks.sh` со сброшенным счётчиком. На
линии, которая переподключается чаще раза в 12 часов, списки не
обновились бы никогда. Повторные ifup чаще чем раз в 6 часов скрипт
пропускает, чтобы дёрганый PPPoE не гонял закачку по кругу.

`use_direct_list` выключен — это отдельный от `chnlist` набор
(`/usr/share/passwall/rules/direct_host`), в нём лежал один `router.test`,
а применялся он раньше всех остальных.

Смена адреса списка в `uci-defaults` тянет за собой удаление скачанного
файла: содержимое из прежнего источника после этого просто неверное.
На стенде так и вышло — планировщик был мёртв из-за старых имён опций,
обновление не отрабатывало ни разу, и в `chnlist` лежали дефолтные
китайские домены, 112 тысяч штук вместо тысячи наших. Маршрутизация
получалась обратной задуманной, и каждый перезапуск PassWall перемалывал
этот том заново.
